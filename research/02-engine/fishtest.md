# Fishtest — proving an engine change is a real improvement

Research date: 2026-09-08. Sources: https://github.com/official-stockfish/fishtest (WebFetch), https://github.com/official-stockfish/fishtest/wiki/Fishtest-mathematics (WebFetch), https://github.com/official-stockfish/fishtest/wiki/Creating-my-first-test (WebFetch), https://github.com/official-stockfish/fishtest/wiki/Fishtest-faq (WebFetch), https://chessprogramming.org/Sequential_Probability_Ratio_Test (via WebSearch), https://www.dogeystamp.com/chess3/ (WebFetch — a hobbyist's independent write-up of running the same methodology outside fishtest's own infrastructure), and `gh api` checks against the fishtest repo for licensing, as cited inline.

## 1. What they do

- Fishtest is "a distributed task queue for testing chess engines" (source: https://github.com/official-stockfish/fishtest README, direct WebFetch). Developers submit a patch/branch; volunteers run a worker program that pulls the opening book, the `fastchess` match-runner, and the engine source, compiles it for the local platform, plays batches of games, and reports results back to a central server.
- The server maintains prioritized test queues, performs the statistical analysis on results as they stream in, and — critically — **decides when a test has reached statistical significance and should stop**, rather than running a fixed number of games (source: same README).
- The statistical engine is **GSPRT**, a generalization of the classical **Sequential Probability Ratio Test (SPRT)** in which "unknown parameters within the statistical hypotheses (H0 and H1) are replaced by their maximum likelihood estimates" (source: https://github.com/official-stockfish/fishtest/wiki/Fishtest-mathematics, direct WebFetch).
- Test bounds are expressed in **normalized Elo**, chosen specifically so "the expected duration of a test [is] dependent only on the chosen bounds, independent of the specific draw ratio or opening book used" (same source) — this is what lets fishtest compare test costs consistently even as the book or the draw rate of the engine changes over time.
- **Standard time controls**, confirmed directly from the "Creating my first test" wiki page: **STC = 10+0.1** (10 seconds base, 0.1s increment), **LTC = 60+0.6**. Other time controls ("40/10", "10+0") are used only "exceptionally," e.g. for time-management-specific testing. Standard tests are single-threaded; **SMP tests run on exactly 8 threads** and are done monthly as a regression check (source: https://github.com/official-stockfish/fishtest/wiki/Creating-my-first-test, direct WebFetch).
- **Default SPRT bounds**, from the same page: for an ordinary functional change, roughly **[0.25, 3.0] Elo at STC** and **[0.0, 3.0] Elo at LTC**; for a simplification/non-regression test (a change expected to be roughly neutral but that must not be a *loss*), roughly **[-1.75, 0.25] Elo**. A developer runs STC first; only if STC passes do they submit the LTC confirmation test; only after both pass does a PR go up against master (same source, full 8-step workflow captured there).
- **Concrete game-count evidence**: cited example test runs on the order of **24,858 games at STC** and **40,789 games at LTC** to reach a decision (source: WebSearch cross-referencing chessprogramming.org and chess.com forum discussion of "Stockfish Dev Data" — an illustrative real example, not a fixed rule; game counts vary per test since SPRT stops adaptively). Fishtest's own FAQ separately notes the throughput unit: "four STC games for a 1-core worker represents about 2 minutes of work, [and] four LTC games represent about 12 minutes" (source: https://github.com/official-stockfish/fishtest/wiki/Fishtest-faq, direct WebFetch).
- **Book selection matters and is tracked as a bias source**: the FAQ explicitly names "selection bias is a book-related effect, patches are more likely to be selected if they perform well with the testing book" as a known caveat (same source). The specific book file(s) fishtest currently defaults to were **not confirmed in this research pass** — flagged **NOT VERIFIED** (the wiki pages fetched referenced book selection as an advanced/configurable option without stating the current default filename).
- Independent of fishtest itself, a hobbyist engine author running the *same methodology* outside fishtest's infrastructure uses the open-source **fastchess** (https://github.com/Disservin/fastchess) directly, with the **8moves_v3.pgn** opening book, an STC-equivalent time control (their example: 8+0.08), SPRT bounds like `elo0=0 elo1=10` for "is this an improvement" or `[-10, 0]` for "did this refactor regress anything," and **Ordo** (https://github.com/michuel/Ordo) to turn a batch of pairwise results into a full Elo leaderboard across many engine versions (source: https://www.dogeystamp.com/chess3/, direct WebFetch). This is the smallest reproducible version of fishtest's methodology and is the concrete template for §6 below.

## 2. Why it works

- **Sequential testing stops as soon as there's enough evidence, in either direction**, instead of committing to a fixed sample size up front. A patch that's clearly bad gets rejected fast (few games); a patch near the boundary takes longer, proportional to how hard the question actually is.
- **Predefining elo0/elo1 before running any games removes the single biggest source of self-deception in engine testing**: you cannot retroactively decide "well, 3 Elo would have counted as a win" after seeing the result — the hypothesis is fixed first, and the LLR (log-likelihood ratio) either crosses the acceptance or rejection boundary or the test keeps running. This directly answers the task's framing: **"it won 7/10" is worthless because 10 games has essentially zero statistical power to distinguish a 5-Elo change from a 50-Elo change from noise** — fishtest's own FAQ states this plainly: "drawing conclusions from an unfinished test is statistically meaningless," and even a *completed* SPRT test carries a designed-in 5% false-positive rate ("error bars are designed to be right 95% of the time. So, conversely, 1 in 20 tests will be an outlier") — meaning even fishtest's rigorous process accepts that 1 in 20 "passes" is noise, which puts a 10-game anecdote's reliability in perspective by contrast (source: https://github.com/official-stockfish/fishtest/wiki/Fishtest-faq).
- **Normalized Elo decouples the test's expected cost from incidental factors** (draw rate, book choice) so bounds chosen once remain meaningful as the engine and testing conditions evolve over years (source: Fishtest-mathematics wiki page).
- **Crowdsourced volunteer compute is what makes tens of thousands of games per test affordable at all.** A single STC test needing ~25k games at "~2 minutes per 4 games on 1 core" is roughly 200+ core-hours; spread across thousands of volunteer workers this resolves in hours, not weeks — a scale advantage a single-team project structurally cannot replicate without either much smaller game counts (looser bounds, more false positives/negatives) or much cheaper games (see §6/§7).

## 3. What they do badly

- **Fishtest's FAQ is explicit that individual passing-patch Elo estimates are biased**: "Elo's estimates of passing patches are biased... only unbiased if one takes *all* patches into account, both passed and non-passed ones" (source: https://github.com/official-stockfish/fishtest/wiki/Fishtest-faq). This is a subtle, easy-to-miss failure mode: reading "this patch passed at +2.1 Elo" as "this patch is worth +2.1 Elo" overstates the true gain, because only patches that happened to test well get reported/kept — a selection effect on top of the statistical test itself.
- **Hardware-mix sensitivity is a real, acknowledged confound**: the FAQ specifically flags that "NNUE vs classical evaluation is very sensitive to the hardware mix present at the time of testing" — meaning a change validated on one distribution of volunteer CPUs is not guaranteed to hold on a materially different hardware population (same source).
- **A 5% false-positive/false-negative rate is baked in by design (α=β=0.05)**, not a bug but a real cost: at Stockfish's cadence of continuous testing, roughly 1 in 20 accepted patches is expected to be noise dressed as signal, and this is never fully resolved — it's a standing, accepted error budget (same source).
- **The whole apparatus assumes a large volunteer compute pool.** Nothing about GSPRT itself requires that, but the *practical* game counts fishtest routinely uses (tens of thousands per test) are calibrated to what a large distributed grid can deliver in hours; the same rigor on a single dev machine is a much slower and more expensive process (see §7).

## 4. What we should copy conceptually

- **Fix elo0/elo1 (or our review-quality equivalent, see §5) before running a single test game** — never adjust the "what counts as an improvement" bar after seeing results.
- **Decide by the log-likelihood ratio crossing a boundary, not by a raw win-count or a fixed number of games.** A test either concludes (pass/fail) or is still running; there is no "it's probably fine, we ran a decent number of games" middle state.
- **Two-stage gating**: a cheap, fast, loose-bounds filter (STC-equivalent) to kill obviously-bad or obviously-neutral changes quickly, and a slower, tighter-bounds confirmation (LTC-equivalent) before anything is actually kept — mirrors fishtest's own STC-then-LTC workflow exactly.
- **Treat "it won N games" as meaningless below whatever N the chosen SPRT bounds actually require**, and say so explicitly in any internal reporting — borrowing fishtest's own FAQ language almost verbatim: never draw conclusions from an unfinished/underpowered test.
- **Track and report the known bias directions**, the way fishtest's FAQ does (selection bias, hardware sensitivity) — a documented list of "known ways this test can mislead us" travels with the methodology, not just the pass/fail number.

## 5. What we can do better

- **Fishtest optimizes exclusively for playing strength (Elo). Our product's actual quality metric is different: game-review usefulness — is the flagged blunder the real blunder, is the suggested best move stable and correct, is the explanation accurate.** A direct fishtest-style SPRT on Elo alone would have told us akimbo's NNUE was an improvement (which, per project background, it was, in Elo terms) and would have said nothing about the fact that it made game review *worse* — the exact case where "stronger" and "better for the product" diverged and only the second one mattered. So the metric we gate on cannot just be win-rate against a baseline build; it needs a **review-quality metric** as the primary signal, with playing-strength SPRT retained only as a secondary sanity gate (a change must not silently break basic play strength, but passing that gate is necessary, not sufficient).
- Concretely, a review-quality metric could be built the same statistical way (GSPRT-style sequential testing on a proportion/score rather than on a win/draw/loss outcome) but scored against: (a) agreement rate between our engine's "best move"/blunder-flag output and a reference engine's top choice on a fixed, curated position set drawn from real games; (b) stability of the suggested best move across small time-budget changes (a move that flips every re-run is a worse teaching signal even at equal Elo); (c), if we ever build human-labeled data (see §8), agreement with human-judged "was this explanation actually useful" ratings. This is a genuinely different target from anything fishtest, nnue-pytorch, or lc0's own testing infrastructure measures — none of them have ever needed to solve for explanatory quality, because none of them ship a game-review product.
- **We can afford tighter, more specific position sets than fishtest's general opening-book approach**, because our test target (review-quality regression) is about specific tactical/strategic categories (missed forks, hung pieces, endgame technique) rather than general playing strength across all of chess — a curated, stratified test set (by theme, the way Lichess tags puzzles — see `01-platforms/lichess.md`) is a more targeted instrument than a generic opening book for *our* question, even though it would be the wrong instrument for fishtest's question.

## 6. What is technically required

A concrete, adoptable protocol, scaled to what a single-team project (not a volunteer grid) can actually run:

1. **A headless test harness.** Our engine already runs in a Web Worker and is perft-validated (per project background), which means it can already be driven outside a browser UI — build a small Node.js harness that instantiates two builds of the engine (the current baseline and the candidate change) and drives them against each other, or against a fixed position set, without any DOM/browser dependency. This mirrors what `fastchess` (used both by official fishtest workers and the independent hobbyist setup in `dogeystamp.com`'s write-up) does for native engines, adapted to our TS/worker architecture.
2. **A fixed, versioned opening/position set**, analogous to fishtest's opening book or the hobbyist's `8moves_v3.pgn` — for playing-strength self-play games, a diverse fixed opening book to avoid degenerate repeated games; for review-quality testing (§5), a separate fixed, tagged position set of real flagged positions.
3. **A sequential test runner implementing GSPRT** (or a simpler classical SPRT to start) over whichever outcome variable is being measured — win/draw/loss pairs for a playing-strength gate, or a scored proportion for a review-quality gate — computing the LLR after each batch and stopping the moment it crosses the accept or reject boundary. This is a well-published, implementable-from-spec algorithm (https://chessprogramming.org/Sequential_Probability_Ratio_Test), not something that needs to be copied from fishtest's GPL-status-unclear codebase (see §9) — and doesn't need to be, since it's math, not code.
4. **Pre-declared bounds for each class of change**, mirroring fishtest's STC/LTC split: a fast, loose-bounds smoke test for "did this obviously break something" run on every change, and a slower, tight-bounds confirmation before anything ships, run only on changes that pass the smoke test.
5. **A leaderboard/aggregation step** (Ordo-equivalent) if we ever compare more than two builds at once, so relative strength across several candidate changes stays on one consistent scale rather than a pile of pairwise-only results.

## 7. What could break

- **We do not have a volunteer grid of thousands of CPUs.** The concrete numbers in §1 (24,858 STC games, 40,789 LTC games for one example test) took fishtest's distributed workers hours; the same game count on a single dev machine, especially if our TS engine in Node is slower per-node than Stockfish's tuned C++, could take substantially longer — this needs to be measured, not assumed, before committing to fishtest-scale bounds for every change. A realistic mitigation is looser bounds (larger elo0/elo1 gap) for routine changes, accepting less sensitivity in exchange for feasible game counts, and reserving tight bounds for genuinely high-stakes changes.
- **A JS/TS self-play test run at reduced depth/time to keep games fast risks not exercising the same code paths as full-strength play** — the classic tension between "fast enough to run often" and "representative of real conditions," which fishtest itself resolves by having two distinct time controls (STC for speed, LTC to confirm at closer-to-real conditions) rather than picking one.
- **SPRT's validity depends on the two things under test differing in only the field being tested.** A branch that mixes a bug fix with an unrelated feature addition muddies what the test result actually means — this is a discipline requirement (small, isolated changes) more than a technical risk, but it is exactly the kind of thing that erodes silently if not enforced.
- **A review-quality metric (§5) is new territory with no existing calibration.** Unlike Elo, which has decades of shared reference points (what a 44-Elo gain "feels like" is well understood across the community), our review-quality score has no external baseline the first time it's built — the bounds chosen for its own SPRT-style test will themselves need calibration against known-good and known-bad changes before they can be trusted, an extra bootstrapping step fishtest's Elo-based test never had to do.

## 8. What we can uniquely do because of Nimiq

- **This is an internal-engineering process, not a user-facing feature, so most of the product's Nimiq-specific advantages (instant payments, wallet-based identity) don't directly apply to the testing methodology itself.** The one genuine, non-forced connection: fishtest's entire model depends on unpaid volunteer compute, sustained purely by community goodwill over many years — a resource a new project cannot assume it has. **Nimiq's feeless, instant micropayments make it economically viable to pay contributors in NIM per verified batch of test games run on their own device**, turning fishtest's volunteer-only model into an incentivized one for a bootstrapping project that doesn't yet have Stockfish's decade of community trust — e.g., a small NIM reward per completed, verified SPRT batch submitted by a real device, paid the moment the batch is verified. This is speculative infrastructure, not a near-term build priority, but it is a genuine asymmetry: no other engine-testing project reviewed here (fishtest, nnue-pytorch's training-data generation, lc0's historical distributed self-play) has ever had a frictionless native payment rail to formalize this with, and Nimiq's rails already exist for us.
- If we ever build the review-quality-labeled dataset described in §5's item (c), the same mechanism (a tiny NIM payment per verified human label) is the direct enabler — covered fully in `nnue-training.md` §8, which is where that specific idea belongs since it's about training/labeling data rather than testing methodology.

- **This is moot for our purposes.** We have no intention of vendoring fishtest's server/worker Python code; the only thing worth adopting is the **SPRT/GSPRT statistical methodology**, which is published mathematics (the Sequential Probability Ratio Test predates fishtest by decades and is documented independently at https://chessprogramming.org/Sequential_Probability_Ratio_Test) and is not copyrightable subject matter regardless of what license, if any, covers fishtest's specific implementation.
