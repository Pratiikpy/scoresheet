# Stockfish — the reference alpha-beta engine

Research date: 2026-09-08. Sources: https://stockfishchess.org/blog/2026/stockfish-19/ (WebFetch + WebSearch cross-check), https://github.com/official-stockfish/Stockfish (WebFetch + `gh`-style tree listing), https://github.com/official-stockfish/networks (WebFetch), the GNU GPL FAQ (https://www.gnu.org/licenses/gpl-faq.html, via WebSearch), the FSFE writeup of *Stockfish v. ChessBase* (https://fsfe.org/news/2022/news-20221212-01.en.html), and targeted WebSearch queries on stockfish.wasm / lila-stockfish-web, as cited inline.

## 1. What they do

- Stockfish is "a free and strong UCI chess engine" derived from Glaurung 2.1, distributed as source + prebuilt binaries with no bundled GUI (source: https://github.com/official-stockfish/Stockfish README).
- **Search core** (`src/`): `search.cpp`/`search.h` (iterative-deepening alpha-beta with the standard modern refinements — null-move, LMR, quiescence, all confirmed present by header includes of `evaluate.h`, `movegen.h`, `position.h`, `thread.h`, `nnue/network.h`, `nnue/nnue_accumulator.h`), `movepick.cpp`/`movepick.h` (move ordering incl. killer/history, `history.h`), `tt.cpp`/`tt.h` (transposition table), `timeman.cpp`/`timeman.h` (time management), `tune.cpp`/`tune.h` (parameter tuning hooks used by fishtest — see `fishtest.md`). Full `src/` file listing confirmed by direct fetch of the GitHub tree (2026-09-08): `attacks.{cpp,h}`, `benchmark.{cpp,h}`, `bitboard.{cpp,h}`, `engine.{cpp,h}`, `evaluate.{cpp,h}`, `history.h`, `main.cpp`, `memory.{cpp,h}`, `misc.{cpp,h}`, `movegen.{cpp,h}`, `movepick.{cpp,h}`, `numa.h`, `perft.h`, `position.{cpp,h}`, `score.{cpp,h}`, `search.{cpp,h}`, `shm.h`, `shm_unix.h`, `thread.{cpp,h}`, `thread_native.h`, `timeman.{cpp,h}`, `tt.{cpp,h}`, `tune.{cpp,h}`, `types.h`, `uci.{cpp,h}`, `ucioption.{cpp,h}`, plus subdirectories `incbin/` (embeds the .nnue file into the binary), `nnue/`, `syzygy/` (endgame tablebase probing), `universal/`.
- **Evaluation** is NNUE-only since Stockfish 12; there is no classical hand-written evaluation fallback left in the current source tree (source: https://github.com/official-stockfish/Stockfish README — the network file is embedded in the binary via `incbin/`).
- **Stockfish 19** (released 2026-09-05): new network **SFNNv16**, which "reduces binary size by eliminating redundant threat features while adding new pawn-pair features," and discontinues the secondary/auxiliary network Stockfish 16.1 had added for positions where that net previously underperformed. Training used **Quantization-Aware Training (QAT)** "across hundreds of billions of positions rescored using a strong Leela net." Claimed strength gain: **"up to 44 points" Elo over Stockfish 18**, winning "more than three times as many game pairs as it loses" in comparative testing (source: https://stockfishchess.org/blog/2026/stockfish-19/, cross-checked via WebSearch against the GitHub release tag `sf_19` and Lichess's own `StockfishNews` blog post referencing the same release).
- **The WASM claim, precisely**: the release notes state "WebAssembly targets" are now supported as a build target, alongside new native targets (RISC-V/RVV, LoongArch/LSX-LASX) and "universal binaries that auto-detect CPU features." **No further technical detail is given in the blog post** — no size figure, no statement about threading/SharedArrayBuffer requirements, no statement about whether this WASM target is single- or multi-threaded (source: https://stockfishchess.org/blog/2026/stockfish-19/, direct fetch). This is *the official engine* adding a WASM compile target to its own build system — separate and additional to the long-standing third-party **lichess-org/stockfish.wasm** project covered below, which has existed independently for years.
- **Third-party browser build — `lichess-org/stockfish.wasm`**: "a WebAssembly port of the strong chess engine Stockfish," demonstrated on Lichess's own analysis board. It uses "the latest WebAssembly threading proposal" and requires two HTTP headers on the top-level page — `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Opener-Policy: same-origin` — plus `Cross-Origin-Embedder-Policy: require-corp` on the included worker/wasm files themselves (source: https://github.com/lichess-org/stockfish.wasm/blob/master/Readme.md, direct fetch). Shipped as three files (`stockfish.js`, `stockfish.wasm`, `stockfish.worker.js`) totalling **~400KB (~150KB gzipped)** (same source). Browser support: full since Chromium 79 / Firefox 79; Firefox 68–78 needs manual flags (same source). The same org also publishes **`stockfish.js`**, described in their own README as "a more portable but single-threaded version" that does not need SharedArrayBuffer at all (source: WebSearch of https://github.com/niklasf/stockfish.js/ + npm package descriptions). A separate community build, Nathan Rugg's `stockfish` npm package, ships a "lite" single-threaded build at roughly **7MB**, "somewhat weaker than the full version" (source: WebSearch of npmjs.com/package/stockfish and related listings — **NOT independently re-verified against the package itself**).
- Universal binaries auto-detecting CPU features, RISC-V/LoongArch support, 1GB Linux huge-page support, an overhauled shared-memory implementation across Linux/macOS/BSD, and stricter position validation with better error reporting round out the Stockfish 19 changelog (source: https://stockfishchess.org/blog/2026/stockfish-19/).

## 2. Why it works

- **Search speed × cheap incremental evaluation.** Bitboard move generation (`bitboard.cpp`, `attacks.cpp`) plus a transposition table (`tt.cpp`) and aggressive move ordering (`movepick.cpp`, killer/history in `history.h`) push the tree exploration rate very high; NNUE evaluation is deliberately architected to be *incrementally updatable* (accumulator pattern — see `nnue-training.md` §2) so most evaluations along the search tree cost only a handful of add/subtract operations, not a full network forward pass. The combination — fast tree walk × near-free eval per node — is why NNUE-Stockfish out-searches its own pre-NNUE classical-eval ancestor at the same node budget.
- **Every change is proven, not assumed.** No patch — search tweak, eval retrain, or parameter change — reaches master without clearing a fishtest SPRT gate (see `fishtest.md`). This is the actual mechanism behind "44 Elo since Stockfish 18": it's the sum of many individually-verified small gains, not one big idea.
- **Runtime hardware adaptation.** Stockfish 19's "universal binaries that auto-detect CPU features" mean one distributed binary picks the fastest code path (AVX-512, AVX2, etc.) for the machine it's running on, rather than forcing users to pick the right download — removing a whole class of "why is my Stockfish slow" support burden and silently protecting the Elo claim across heterogeneous hardware (source: https://stockfishchess.org/blog/2026/stockfish-19/).
- **Discontinuing the secondary network** in SFNNv16 is itself evidence of the same discipline in reverse: Stockfish 16.1 had shipped a second, position-dependent network, found it underperformed in some position classes, and *removed* it in 19 rather than patching around it — willingness to delete complexity that isn't earning its keep (source: https://stockfishchess.org/blog/2026/stockfish-19/).

## 3. What they do badly

- **The evaluation is a black box.** Since NNUE fully replaced the classical hand-written evaluation in Stockfish 12, there is no human-legible decomposition of *why* a position scores the way it does — no "material +0.3, king safety −0.2, mobility +0.1" that a game-review feature could narrate to a learner. This is precisely the failure mode our own project already hit and rejected when it ported akimbo's NNUE, verified it was a stronger player, and still rejected it *because it made game review worse* (per project background) — Stockfish is optimized for exactly one axis (playing strength) that is not our product's axis (review quality/legibility).
- **Complexity is a real cost to entry.** 40+ source files plus three major subsystems (`nnue/`, `syzygy/`, `universal/`) means safely touching Stockfish's own code requires deep, engine-specific expertise, and *every* change must clear an SPRT gate that itself needs a large, distributed compute grid to run at reasonable speed (see `fishtest.md` §6–7) — a barrier a solo team or small org cannot easily replicate.
- **No instructive/explanatory output by design.** Stockfish's UCI protocol reports a score, a principal variation, and search stats — nothing shaped for teaching. Any "explain this move" feature built on Stockfish output is bolted on externally (this is exactly what Lichess and chess.com do, in their own proprietary layers, not in Stockfish itself).
- **The official WASM target's actual browser behavior is unstated.** The Stockfish 19 blog announces WASM support as a bullet point with zero operational detail — no confirmation of thread-safety, SharedArrayBuffer needs, or size. Treating this as "browser-ready" without testing it directly would be an assumption, not a verified fact (source: https://stockfishchess.org/blog/2026/stockfish-19/, direct read — **this gap is real and reported here as a gap, not filled in**).

## 4. What we should copy conceptually

- **Prove every change against a baseline before keeping it** — the SPRT discipline described fully in `fishtest.md`. This is the single highest-value thing to copy, independent of engine architecture.
- **Runtime capability detection, applied to our own constraints.** Stockfish detects CPU features and picks a code path; our equivalent is detecting Web Worker / WASM / SharedArrayBuffer support at startup inside a Nimiq Mini App WebView and falling back gracefully (single-threaded search, reduced depth/time budget) rather than assuming a capability that may not exist in that WebView (see §7).
- **The incbin-style "one artifact, embedded data" pattern** for the transposition table/opening-book-equivalent data our engine ships, if any — bundling data into the binary/bundle rather than a separate fetch, to avoid a runtime dependency that can silently fail to load.
- **The discipline of deleting a component that doesn't earn its keep** (the SFNNv16 secondary-network removal) — directly validates our own prior decision to reject akimbo's NNUE once it was shown not to serve the product goal, rather than keeping it "because it's stronger."

## 5. What we can do better

- **Legible evaluation is a product feature for us, not a discarded requirement.** Stockfish deliberately has no classical eval left to fall back on; we can keep (or build) an eval whose terms are named and explainable specifically because our product goal is teaching/game-review quality, not maximum Elo. This is not a smaller version of what Stockfish does — it's optimizing for an axis Stockfish's own team has stated interest in but does not ship (their classical eval was retired, not maintained, and was never exposed as a teaching tool even when it existed).
- **We can design the "what could I have played instead" narrative in, rather than reconstruct it after the fact from an opaque score**, because our search and eval stay classical/inspectable — the same PV, killer-move, and history-table machinery Stockfish also uses (and we already have, per project background) is naturally narratable when the eval terms behind it are named.
- **We do not need a distributed fishtest-scale grid to validate correctness** the way Stockfish's search does, because our target is a much narrower, well-specified surface (a 0x88 alpha-beta engine with perft validation already in place) — we can adopt the *methodology* at a scale that matches a single-team project (see `fishtest.md` §6 for the concrete adaptation).

## 6. What is technically required

- To run Stockfish itself (not our own engine) inside a browser at all, one of: (a) the official Stockfish 19 WASM build once its operational characteristics are actually tested (unverified per §1/§3), or (b) `lichess-org/stockfish.wasm`, which needs Emscripten's pthreads/WebAssembly-threads output, `SharedArrayBuffer`, and the exact `Cross-Origin-Embedder-Policy: require-corp` + `Cross-Origin-Opener-Policy: same-origin` header pair on the top-level document *and* `Cross-Origin-Embedder-Policy: require-corp` on the served worker/wasm files (source: https://github.com/lichess-org/stockfish.wasm/blob/master/Readme.md), or (c) a single-threaded fallback build (`stockfish.js` from the same org, or Nathan Rugg's ~7MB "lite" build) that needs neither SharedArrayBuffer nor those headers, at the cost of using only one core.
- Setting those COOP/COEP headers requires control over the HTTP response headers of the page that hosts the engine — normal on a website you control, **not guaranteed inside a Mini App WebView** (see §7).
- None of this is required for our own shipped TS/0x88 engine, which is not WASM and has no such header dependency; it only becomes relevant if we ever want to *run* Stockfish itself in-browser (e.g., as a live "compare to Stockfish" feature) rather than only offline as a testing oracle.

## 7. What could break

- **This is the decisive point the task called out, and it breaks specifically for us.** Nimiq Mini Apps run inside a mobile WebView embedded in the Nimiq wallet app, not as a normal top-level browser tab we control the HTTP response headers for. `NIMIQ_DEV_DOCS_FULL_REFERENCE.md` (per project CLAUDE.md) already documents a "localhost-in-WebView gotcha" for this exact class of platform constraint. Setting `Cross-Origin-Embedder-Policy`/`Cross-Origin-Opener-Policy` on the *top-level* response requires either (a) our own server sending those headers on the page the Mini App loads, which may or may not be possible depending on how Nimiq's Mini App host frames/loads our content, or (b) it is out of our control entirely if the WebView's document is served by Nimiq's own infrastructure rather than ours. **This was not directly tested against an actual Nimiq Mini App WebView in this research pass — flag as NOT VERIFIED whether COOP/COEP headers propagate correctly through the Nimiq Mini App hosting layer.** The concrete implication: a multi-threaded WASM Stockfish (`lila-stockfish-web`/`stockfish.wasm`) may silently degrade to single-threaded (or fail outright) inside the Mini App WebView exactly as the Lichess docs warn happens whenever the headers are misconfigured (source: https://github.com/lichess-org/stockfish.wasm/blob/master/Readme.md — "Without those headers correctly configured server-side, the engine silently falls back to single-threaded mode" per WebSearch synthesis of the same README + issue #31 discussion). The single-threaded fallback build sidesteps this entirely but is slower and, per §1, one popular single-threaded variant is ~7MB — a real payload cost on mobile data.
- **Silent degradation is worse than a hard failure** for a product decision: if COOP/COEP isn't set, a multi-threaded WASM build doesn't error, it just runs slower, which could look like "our engine is bad" during testing rather than surfacing as a clear header-misconfiguration bug.
- **The official Stockfish-19-native WASM target is entirely unverified for browser use** (§1, §3) — if we ever depend on it specifically (as opposed to the long-standing lichess.org fork), that dependency itself is a research gap, not a solved problem.

## 8. What we can uniquely do because of Nimiq

- **Keep Stockfish server-side only, and monetize deep analysis per-request with Nimiq micropayments**, instead of shipping any WASM Stockfish build to the client at all. This sidesteps §7's COOP/COEP/WebView uncertainty completely (no client-side WASM engine, no header dependency, no GPL-distribution question — see §9) while still offering "Stockfish-strength deep review of this game" as a paid feature: the client sends a game/position, our server runs Stockfish (or our own engine at higher depth), and the result is unlocked by a feeless NIM/USDT payment sized appropriately for a single review request. Nimiq's instant, feeless settlement (per `WHAT_NIMIQ_WANTS_VERBATIM.md`/`CYCLE_2_PRIMARY_SOURCE_INTEL.md`, Nimiq/EVM must be the core payment rail) makes a sub-cent-to-cent-sized "unlock one deep review" transaction viable in a way a card-processor minimum fee never would be.
- This is simultaneously the licensing-cleanest option (§9) and a genuine product differentiator: neither Lichess (donation-funded, no payment rail) nor chess.com (subscription-gated, not per-request) offers pay-per-deep-review at Nimiq's transaction cost and speed.

## 9. Licence and reuse verdict

| Component | Licence file / evidence | SPDX id (as stated) | Verdict |
|---|---|---|---|
| Stockfish engine source (`Stockfish/src`) | `Copying.txt` | **GPL-3.0** (confirmed via WebFetch of the repo README, which states: "whenever you distribute Stockfish in some way, you MUST always include the license and the full source code") | **Not embeddable in our MIT bundle.** Copying source into our TS engine, or statically linking a compiled Stockfish into our client bundle, makes the combined work a GPL derivative — incompatible with keeping the repo MIT. |
| Official Stockfish `.nnue` trained network files | `official-stockfish/networks` repo, `LICENSE` file | **CC0-1.0** — repo states verbatim "All networks in this repository were uploaded by the authors under the CC0 license" (confirmed via direct WebFetch of https://github.com/official-stockfish/networks, 2026-09-08) | **Public-domain data, but practically useless to us.** The weight *file* itself carries no copyleft, but it only has meaning when fed through Stockfish's GPL inference code in the exact quantized format Stockfish expects — and we already rejected NNUE for this product on quality-of-review grounds independent of licensing (see `nnue-training.md`). Noted for completeness, not recommended for use. |
| `lichess-org/stockfish.wasm` (and sibling `stockfish.js`) | README states "Thanks to the Stockfish team for sharing the engine under the GPL3" | **GPL-3.0** (inherits from Stockfish; confirmed via direct WebFetch of the Readme.md) | Same GPL constraints as the engine itself — see rows below for what's actually permitted with a GPL binary. |
| fishtest (methodology, not code we'd use) | Checked `official-stockfish/fishtest` repo root via `gh api` (2026-09-08): **no `LICENSE` file present**, and GitHub's license-detection API returned no license classifier | **No stated licence at repository level** (verified absence, not an oversight in this research — the repo root listing contains `AUTHORS`, `README.md`, `CONTRIBUTING.md`, `docs`, `server`, `worker`, no `LICENSE`) | Moot for us either way: we would only ever adopt fishtest's *statistical methodology* (SPRT/GSPRT), which is published mathematics, not copyrightable code, and is documented independently on the Chess Programming Wiki (https://chessprogramming.org/Sequential_Probability_Ratio_Test) — see `fishtest.md`. |

**What GPL-3.0 actually permits and forbids for us, precisely:**

1. **Private/internal use triggers zero GPL obligations.** The GNU GPL FAQ is explicit: "You are free to make modifications and use them privately, without ever releasing them... An organization can make a modified version and use it internally without ever releasing it outside the organization" (source: https://www.gnu.org/licenses/gpl-faq.html, via WebSearch synthesis, cross-checked against multiple FAQ mirrors). **Using Stockfish purely offline as a testing/scoring oracle for our own engine — never distributed, never shipped to a single end-user device — is completely unencumbered.** This is the safest and most valuable use case for us: run official Stockfish locally/server-side to score our own move quality and game-review accuracy, with no licensing exposure whatsoever.
2. **Running Stockfish server-side and serving only its output (an evaluation number, a suggested move) to end users over our own API is *using* Stockfish, not distributing it**, and does not require us to open-source our own server code — this is the exact model WebSearch confirms Chess.com and Chessable use today ("commercial platforms can use it without publishing their entire codebase, as long as they're running Stockfish as a separate engine," synthesized from multiple sources incl. Chess.com's own forum discussion of the topic). This is the model recommended in §8.
3. **Shipping a WASM Stockfish binary to the client, unmodified, as a separate file/worker that our MIT code talks to over the UCI-style protocol, is the FSF's own "mere aggregation" case** — "putting them side by side on the same CD-ROM or hard disk... if one of the programs is covered by the GPL, it has no effect on the other program," and "pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs" (source: FSF GPL FAQ / GPLv3 wiki, via WebSearch synthesis). A Web Worker exchanging UCI text commands over `postMessage` is architecturally the same class of "separate program, narrow interface" relationship. **This is a real, community-relied-upon interpretation (it's exactly how Lichess and chess.com ship Stockfish today) but it is an interpretive FSF position, not case law specific to this exact scenario — treat as strong precedent, not a guarantee.** If we do this: (a) the vendored Stockfish files stay GPL-3.0, clearly labeled, with `Copying.txt` included; (b) our MIT `LICENSE` cannot and must not claim to cover those files; (c) the repo becomes genuinely mixed-license and must say so plainly (a `THIRD_PARTY_LICENSES` note naming exactly which files are GPL-3.0 and why); (d) we must not *modify* the Stockfish binary/source in any way we then distribute — the moment we patch it, we owe corresponding source under GPL for that modified portion.
4. **The one thing that is unambiguously forbidden**, and the exact failure mode of the *Stockfish v. ChessBase* case: distributing a **modified/derivative** build of Stockfish without complying with GPL (informing users of the license, making corresponding source available). The FSFE's own account: ChessBase shipped Fat Fritz 2 and Houdini 6 as derivative works of Stockfish "without informing all its users" they were using GPL-licensed software; the November 2022 settlement imposed a one-year distribution ban, a mandatory Free Software Compliance Officer, a public registry of GPL components, and financial penalties for future violations (source: https://fsfe.org/news/2022/news-20221212-01.en.html, direct WebFetch). **We do not intend to modify Stockfish's source at all, so this specific risk does not apply to any plan considered here** — but it is the concrete evidence that GPL enforcement against exactly this class of chess-engine product has real teeth and has been tested in practice.

**Net verdict:** the licensing-cleanest and product-best option, per §8, is to never ship Stockfish (or any GPL WASM build) to the client at all — use it only as an offline/server-side testing oracle (§9.1, fully unencumbered) and, if a "deep Stockfish review" feature is ever wanted for end users, serve it from our own server as output-only (§9.2), monetized per-request via Nimiq. Shipping the unmodified official WASM build client-side is legally arguable via mere-aggregation precedent (§9.3) but adds real licensing bookkeeping (mixed-license repo, third-party notices) and the unresolved WebView/COOP-COEP risk from §7 — worse on both axes than the server-side-only path.
