# Lila — the architecture

Research date: 2026-09-08. Sources: `gh api` against `lichess-org/lila`, `lichess-org/scalachess`, `lichess-org/lila-ws`, `lichess-org/lila-openingexplorer` (directory listings and file contents pulled via the GitHub REST API, not scraped HTML — every module list below is an exact directory listing, not a summary), plus WebFetch on the lila GitHub repo page and WebSearch for behavior not visible from file names alone. All claims below are sourced; anything inferred purely from a filename (not confirmed by reading the file) is marked as such.

## 1. What they do

Lila ("li[chess in Sca]la") is the monolithic Play-Framework/Scala 3 application that serves lichess.org. It is **not microservices** — it is a large modular monolith (85 top-level modules under `modules/`) plus a small number of purpose-built satellite services that are separate repos/processes:

- **`lila`** (this repo) — the web app, HTTP API, business logic, MongoDB access. Scala 3, Play 2.8 (modified), Pekko streams for async, Scalatags for templating (source: WebFetch of the lila GitHub page).
- **`lila-ws`** — a separate Scala/Akka process that owns every websocket connection. Flow: `lila <-> redis <-> lila-ws <-> websocket <-> client`; lila never talks to a browser socket directly, it publishes to Redis and lila-ws fans that out (confirmed via `gh api` README fetch: "Redis as a message broker for pub/sub communication with the main Lila application"). It explicitly documents that it trusts `X-Forwarded-For` and must sit behind a reverse proxy.
- **`scalachess`** — a standalone, side-effect-free, immutable Scala library (MIT) that is lila's chess rules engine, imported as a dependency rather than living inside `modules/`. Split into its own SBT modules: `core` (rules/move-gen/FEN-PGN-UCI/variants/bitboards), `rating` (Elo + Glicko-2), `playJson` (Play-Framework JSON codecs for the above), `tiebreak` (tournament tiebreak math), `test-kit`, `bench` (JMH benchmarks) — confirmed via `gh api repos/lichess-org/scalachess/contents`.
- **`lila-openingexplorer`** — a standalone Rust/RocksDB service (see `07-data/opening-explorer.md`), reachable by lila only over its public HTTP API, not embedded.
- **`fishnet`** — not a lila submodule but an external distributed worker pool: `modules/fishnet` in lila is the *coordinator* (`FishnetApi.scala`, `FishnetPlayer.scala`, `Work.scala`), which hands out analysis jobs to a fleet of client machines running Stockfish and collects results back — this is how "free unlimited cloud analysis" is possible without lila's own servers running the engine.

**Module inventory** (all 85 directories under `modules/`, exact, via `gh api repos/lichess-org/lila/contents/modules`):

## 2. Why it works

- **Monolith-plus-satellites is a deliberate boundary, not laziness.** Everything that needs the full domain model and MongoDB (game state, tournaments, puzzles, studies, users) lives in one deployable; only the two things with genuinely different scaling/latency/language needs — persistent websocket fan-out (lila-ws) and a huge append-only positional index (opening explorer) — are split out. This avoids premature microservice overhead while still isolating the two components that would otherwise dominate the main app's resource profile.
- **Chess logic is a pure, dependency-free library, imported not embedded.** Because `scalachess` is "entirely functional, immutable, and free of side effects" (its own README, confirmed via `gh api`), it can be property-tested, JMH-benchmarked in isolation (`bench` module, `Jmh / run` targets), and reused unmodified across scalachess-only and lila contexts, in Puzzle generation, in Insights indexing, and in the analysis board — one correctness surface instead of many.
- **The websocket layer is decoupled from business logic via Redis pub/sub**, so lila can be restarted/redeployed without dropping every live connection, and lila-ws can be scaled independently of request-handling capacity — a real operational win for a product whose core value (live games) is inherently a long-lived-connection workload.
- **Rating and tiebreak math live in the same pure library as the rules engine** (`scalachess/rating`, `scalachess/tiebreak`), not scattered through the web app — meaning the numbers that decide who's "better" are computed by code with no HTTP/DB coupling, testable and benchmarkable in total isolation.
- **Analysis compute is federated (fishnet), not centrally hosted.** Volunteer/community machines run Stockfish; lila's job is coordination (`FishnetApi`, `FishnetLimiter`, `FishnetRedis`) not computation — this is the single biggest reason "unlimited free analysis" is financially sustainable for a donation-funded nonprofit.
- **Fair-play detection is modularized exactly like everything else** (`modules/irwin` for engine-correlation, a corresponding `Kaladin` system in a separate repo for behavior-anomaly) and reports into the same moderation queue module (`modules/report`) that handles every other abuse signal — one human review surface for many machine signals.

## 3. What they do badly

- **85 top-level modules in one deployable is a lot of coupling surface**, even if each module is internally clean; a change to `game` or `round` (game lifecycle) has wide blast radius by construction, because so much else (`insight`, `puzzle`, `tv`, `evalCache`, `study`) consumes game state directly. This is the classic modular-monolith tradeoff and Lila is squarely on the "big monolith" end of it.
- **Two independently-evolving cheat-detection systems living in two repos with different training approaches (Irwin: engine-PV-correlation ML in Python/TensorFlow; Kaladin: CNN over Insights metrics in a separate AGPL repo) is duplicated infrastructure** — separately deployed, separately maintained ML pipelines with overlapping goals. Reasonable given they catch different signal classes, but it's real operational overhead that a smaller team would struggle to sustain.
- **The opening explorer's RocksDB store has admin endpoints that must be manually reverse-proxy-whitelisted** ("only `/masters`, `/lichess`, and `/player`" should be public — everything else needs infra-level protection, per its own README) — security-by-convention at the infra layer rather than the application enforcing it, a footgun for anyone standing up their own instance.
- **lila-ws explicitly trusts `X-Forwarded-For`** and documents that it "must only operate behind a reverse proxy" — correct for Lichess's own deployment, but a sharp edge for anyone deploying the open-source stack without matching infra exactly.

## 4. What we should copy conceptually

- **Separate the long-lived connection layer from the request/business-logic layer early**, even at small scale — a lightweight pub/sub bridge (Redis or equivalent) between "authoritative game state" and "who's currently subscribed to updates" avoids coupling reconnect/backpressure handling into the same code path as move validation.
- **Keep the rules/rating engine as a pure, dependency-free, independently-testable/benchmarkable library**, decoupled from HTTP, DB, and UI concerns — this is exactly the shape a "cryptographically signed, independently recomputable rating" needs: a pure function from signed game history to rating, with zero hidden state, so it *can* be recomputed by a third party from nothing but public inputs.
- **Federate compute you can't afford to centralize.** Fishnet's coordinator/worker split is the template for anything expensive (engine analysis) that doesn't need to run on our own infrastructure.
- **One moderation/report surface for every integrity signal**, regardless of which detector produced it — don't build a bespoke review UI per detection method.
- **Module boundaries drawn around domain concepts (game, round, tournament, puzzle, insight), not around technical layers** — makes it obvious where new domain logic belongs.

## 5. What we can do better

- **Make the rating function's inputs and outputs cryptographically verifiable, not merely internally pure.** Scalachess's Glicko-2 implementation is pure and testable, but its inputs (game results) and outputs (rating numbers) are asserted by lila's MongoDB with no signature chain — anyone auditing a Lichess rating has to trust the Lichess server end-to-end. We can keep the "pure function over signed inputs" property Lila already has for its math, and additionally sign the inputs (move list + result + timestamp, signed by both players' keys or a verifiable game record) so the *entire* chain — not just the arithmetic — is independently reproducible by someone with no access to our database.
- **A much smaller module count for a focused mobile-first app.** Lila's 85-module sprawl serves an enormous multi-feature platform; a chess Mini App with one clear differentiator needs maybe 6-10 domain modules (game, rating, matchmaking/pairing if any, wallet/payment integration, puzzle-or-whatever-hook) — small enough that one person can hold the whole system in their head, which is itself a resilience property Lila at its scale no longer has.
- **No server-owned account as the root of game/rating identity.** Lila's `modules/user` + `modules/security` (Authenticator, PasswordHasher, SessionStore, OAuth) is a full traditional account system generating substantial module surface (auth, sessions, email verification, disposable-email detection, IP trust, GeoIP, Tor detection — 30+ files in `modules/security` alone, per `gh api repos/lichess-org/lila/contents/modules/security/src/main`). A wallet-address-as-identity model eliminates almost that entire module's worth of complexity and attack surface for us.

## 6. What is technically required

Mapped to Lila's own module boundaries, adapted for a small MIT chess app with no server-owned account:

**Game lifecycle / round / game state** (Lila's `modules/round` + `modules/game`):
- `modules/round` owns the *live* game: move application, clock, draws/resignation/abort, takebacks, rematch offers, spectator move-streaming. Confirmed file list (`gh api repos/lichess-org/lila/contents/modules/round/src/main`): `RoundAsyncActor.scala` (the live per-game actor — one actor instance per in-progress game, holding authoritative state in memory), `RoundGame.scala`, `RoundSocket.scala` (bridge to lila-ws), `MovePlayer.scala`, `Takebacker.scala`, `Rematcher.scala`, `Moretimer.scala`, `MoveLatMonitor.scala`/`LagTracker` (scalachess) for lag compensation, `Finisher.scala` (end-of-game resolution: rating update trigger, `PerfsUpdater.scala`), `CorresAlarm.scala`/`CorrespondenceEmail.scala` (correspondence-specific timers/notifications), `SelfReport.scala` (client-side anomaly self-reporting, likely anti-cheat signal — **NOT VERIFIED** in depth), `FarmBoostDetection.scala` (rating-farm/sandbagging detection — **NOT VERIFIED** in depth, filename only).
- `modules/game` is the persisted/historical record once a round concludes (search-indexed via `modules/gameSearch`).
- Architectural takeaway: **the authoritative live-game state is an in-memory actor (one per game), not a DB row re-read on every move** — moves are applied to the actor's in-memory state and persisted asynchronously/incrementally. A small app needs at minimum: an authoritative move-validation point (using scalachess or an equivalent pure rules engine), a clock model, and an explicit end-of-game hook that triggers rating computation.

**Realtime transport** (`lila-ws`, bridged via `modules/socket` + `modules/room`):
- lila never opens a websocket itself. `modules/socket` is the lila-side abstraction that publishes state-change events to Redis; `lila-ws` (separate process, separate repo) holds actual client connections and fans out. `modules/room` (chat backing) rides the same transport for game/tournament chat.
- Takeaway: even a modest app benefits from separating "who is currently connected and needs pushes" from "what is authoritative game state" — a pub/sub layer (doesn't need to be Redis) between them means the transport can restart without losing game state, and game logic never blocks on socket I/O.

**Rating** (`scalachess/rating` + lila's `modules/rating` + `modules/perfStat`):
- `scalachess/rating/src/main/scala`: `Elo.scala` and a `glicko/` package (`GlickoCalculator.scala`, an `impl/` subpackage, `model.scala`) — confirmed via `gh api repos/lichess-org/scalachess/contents/rating/src/main/scala`. This is the pure math, MIT-licensed, directly portable.
- Lila's own `modules/rating` and `modules/perfStat` wrap that pure calculator with per-perf-type (per speed/variant) rating history, decay, and leaderboard eligibility rules (from FAQ research: leaderboard requires rating deviation < 75 standard / < 65 variants; provisional players start "1500 ± 1000" and show a "?" while deviation > 110).
- Takeaway for our differentiator: keep the Glicko-2 (or chosen algorithm) implementation as pure and dependency-free as scalachess's is, version it explicitly, and treat "which version of the algorithm produced this rating" as part of what gets signed — Lila's own system has no such requirement because trust is centralized in its database, but ours must.

**Tournaments** (`modules/tournament` for Arena, `modules/swiss` for Swiss):
- Arena: `AutoPairing.scala`, `Duel.scala`, `WaitingUsers.scala`, `Revolution.scala` (repeated pairing waves), `arena/` subpackage, `TournamentScheduler.scala`, `TournamentShield.scala` (recurring "shield" trophies) — confirmed listing via `gh api`.
- Swiss: `PairingSystem.scala` (wraps the external FIDE-standard `bbPairings` Dutch-system implementation), `SwissTrf.scala` (Tournament Report File — the FIDE interchange format, meaning Lichess Swiss results are directly importable into official FIDE-adjacent tooling), `SwissScoring.scala`, `SwissBoard.scala`, `SwissDirector.scala` — confirmed listing.
- Takeaway: Arena-style continuous pairing needs a live matchmaking loop keyed on current standings; Swiss-style needs a full-tournament-state pairing algorithm run once per round — these are structurally different problems and Lila correctly keeps them in separate modules rather than unifying them.

**Puzzles** (`modules/puzzle`):
- Confirmed file list includes `PuzzleSelector.scala` (serving the next puzzle), `PuzzleDifficulty.scala`/`PuzzleTier.scala`/`PuzzleTrust.scala` (quality-gating auto-generated puzzles before they're shown to real users), `PuzzleTagger.scala`/`PuzzleTheme.scala` (theme classification), `PuzzleFinisher.scala` (rating update on solve, mirroring `round`'s `Finisher`), `PuzzleStreak.scala`, `PuzzleDashboard.scala`, `PuzzleReplay.scala`.
- Takeaway: puzzle generation-from-games and puzzle-serving-with-its-own-rating are architecturally the same pattern as game-rating — "treat this interaction as a rated contest against a fixed opponent (the puzzle), and update both sides' ratings" — reusable pattern if we ever want a solo/asynchronous rated mode.

**Analysis** (`modules/analyse` + `modules/fishnet` + `modules/evalCache`):
- `modules/evalCache`: `EvalCacheApi.scala`, `EvalCacheEntry.scala` — a shared cache of previously-computed engine evaluations keyed presumably by position, so identical positions analyzed by different users don't recompute.
- `modules/fishnet`: the coordinator for the distributed Stockfish worker pool (`FishnetPlayer.scala`, `Work.scala`, `FishnetLimiter.scala` for quota, `FishnetRedis.scala` for job queueing).
- Takeaway: analysis-on-demand at any scale benefits from a cache-first design (position → eval, content-addressed) before ever dispatching to compute.

**Fair play** (`modules/irwin` + external `kaladin` repo + `modules/report`):
- `modules/irwin` (confirmed listing): `IrwinApi.scala`, `IrwinReport.scala`, `IrwinRequest.scala`, `IrwinStream.scala`, `IrwinThresholds.scala`, and — notably — `KaladinApi.scala`/`KaladinUser.scala` living *inside* the irwin module, meaning lila talks to both detectors through one integration point even though Kaladin is a physically separate service/repo.
- `modules/report`: `Report.scala`, `ReportApi.scala`, `ReportScore.scala`, `ReportThresholds.scala`, `Room.scala`, `Automod.scala`, `AutoAnalysis.scala` — the shared moderation inbox that both automated detectors and human reports feed into, with a scoring/threshold system to prioritize the queue.
- Takeaway: **one integration surface for "this game/player looks suspicious," fed by multiple independent detectors, feeding one human review queue with automatic scoring** — directly reusable pattern regardless of what our own detectors look like.

**Storage**:
- MongoDB is the primary datastore (confirmed via WebFetch of the lila repo page: "Database: MongoDB (12+ billion games)"); Elasticsearch backs full-text search (`modules/search`, `forumSearch`, `studySearch`, `teamSearch`); Redis is the pub/sub/cache fabric between lila and lila-ws and inside fishnet's job queue (`FishnetRedis.scala`); the opening explorer uses its own embedded RocksDB, entirely separate from lila's MongoDB.
- Takeaway: the "one big document per game" model (MongoDB) suits chess game records well (irregular length, nested move tree, easy to append) — worth deliberately choosing rather than defaulting to a heavily normalized relational schema, unless the recomputable-rating requirement pushes toward something more structured/append-only (e.g., an event log of signed moves) for verifiability reasons — that tension is itself a design decision to make explicitly, not inherit from Lila.

## 7. What could break

- **In-memory per-game actor state (`RoundAsyncActor`) means a server crash mid-game is a real event to handle** — Lila must have (though not confirmed by file inspection alone — **NOT VERIFIED** in depth) some persistence/recovery path for in-flight games; any small app copying this pattern needs an explicit answer for "server restarts mid-game" from day one, not as an afterthought.
- **Redis as a single point of coordination between lila and lila-ws** is a dependency that, if down, breaks all realtime delivery even if the authoritative game state (in lila) is fine — an availability risk inherited by anyone copying the pattern without also planning for Redis failure modes.
- **A pure, versionless rating function is not enough for our differentiator — it must be explicitly versioned or replays diverge.** If we ever tune Glicko-2 parameters (as Lila's own scalachess presumably has done across its history — **NOT VERIFIED**, no changelog inspected) without a version tag baked into the signed record, independent recomputation from old signed games will silently produce different numbers than what was originally shown, defeating the entire "independently recomputable" promise.
- **Federated compute (fishnet-style) requires trust in worker honesty** — if we ever offload eval/verification work to untrusted third parties the way fishnet offloads Stockfish analysis to volunteers, we inherit the same problem Lila has (a worker could return wrong evals) and need equivalent mitigations (worker reputation/quorum), which Lila's own docs don't fully surface — **NOT VERIFIED** what integrity checks fishnet applies to worker output.

## 8. What we can uniquely do because of Nimiq

- **Replace "trust the MongoDB-backed rating" with "trust a signature chain anyone can verify."** Lila's `RoundAsyncActor` → `Finisher` → rating-update pipeline is architecturally sound (pure math, clean module boundary) but terminates in a database write nobody outside Lichess can audit. Our equivalent pipeline can terminate in a signed, publishable record instead — same shape, provably different trust model.
- **Skip the entire `modules/security`-sized account subsystem** (30+ files: password hashing, session store, email verification, disposable-email/IP/Tor detection) by using wallet-address identity as the root — smaller attack surface and less code to get right, precisely because Nimiq's wallet *is* the account.
- **Settle stakes/wagers directly inside the same event that would otherwise just be a `Finisher.scala`-style rating update** — game-end and payment-settlement can be the same atomic step when the payment rail is native to the platform, something Lila's donation-funded, non-monetary model never had to design for.
