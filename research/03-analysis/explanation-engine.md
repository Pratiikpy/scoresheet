# The "Why?" feature — a concrete, implementable design

Scope: given a position, the move the player played, and the engine's preferred move (both already
produced by our own MIT engine per `chess/SPEC.md` Part K1/K2, with per-move evaluation, accuracy and
ACPL already computed in `packages/core/src/analysis.ts` and displayed with engine arrows in
`apps/web/src/study-screen.ts`), design a feature that answers "why was this better/worse?" in one
short, true sentence. This file assumes `03-analysis/coaching.md`'s survey; it does not re-derive it.
The one constraint that shapes every decision below: **a sentence must never be generated by a
language model from the position itself — it must be assembled from facts a deterministic detector
has verified.** §6 and §7 are the load-bearing sections.

## 1. What they do

The closest working precedents, narrowed to the ones that actually detect-then-describe rather than
freely generate:

- **ChessGrammar**, a third-party FEN/PGN tactics API, runs "fast geometric detection" at depth 1 to
  find pattern candidates (~5ms/position) across ten patterns — fork, pin, skewer, discovered attack,
  double check, back-rank mate, smothered mate, deflection, interference, trapped piece — then a
  depth-2 pass "verifies that the tactic works against best defense by computing forcing sequences,"
  built on `python-chess` with no engine dependency at runtime for the geometric pass.
  Source: https://dev.to/stevejvv/i-built-an-api-that-detects-chess-tactical-patterns-from-fen-and-pgn-5ef0.
  No algorithmic detail beyond this two-phase description, no accuracy numbers, and **no licence** is
  published — treated below as evidence the approach works, not as a spec to port.
- **`python-chess`** (GPL-3.0) exposes the exact primitives a detector needs for free: `is_pinned(color,
  square)` and `pin(color, square)` return whether/how a piece is absolutely pinned to its king,
  returning the mask of squares along the pinning ray; `attackers(color, square)` returns every
  attacker of a square for a colour, with the documented caveat that **a pinned piece still counts as
  an attacker** — the same trap applies to counting defenders, and is addressed in §7.
  Source: https://python-chess.readthedocs.io/en/latest/core.html;
  https://github.com/niklasf/python-chess/issues/375
- **Concept-guided commentary** (arxiv.org/html/2410.20811v1, surveyed in `coaching.md`) establishes
  the load-bearing pattern this design copies: score a fixed set of concepts *before* the move and
  *after* the move, and only describe the concepts whose score moved most. It reaches 0.60/1.0
  correctness with this grounding, against 0.36 for ungrounded generation — still short of "never
  false," which is exactly why this design goes further and drops language-model generation of the
  factual claim entirely (see §6).
- **Caïssa AI** (GPL-2.0, arxiv/KI2025, surveyed in `coaching.md`) adds a verification pass that
  decomposes each generated sentence back into structured claims and checks them against a symbolic
  layer (Prolog + Neo4j) before the sentence reaches the user, reporting a 93.13% tactic hit rate.
  The pattern worth keeping — verify before emitting — is copied here without the heavy
  Prolog/Neo4j/cloud-LLM infrastructure, which cannot run inside a browser Web Worker in an MIT
  bundle. Source: https://www.researchgate.net/publication/395158512
- **`python-chess-annotator`** (GPL-3.0, detailed in `coaching.md` §1) is the base signal this design
  already has for free: an eval delta between the played move and the engine's best move, mate scores
  folded into the same scale, and a minimum-delta gate before anything is emitted at all — exactly the
  gate this design reuses in §6.

## 2. Why it works

- **The detect-then-verify pattern is the only one in the literature with acceptable correctness.**
  Grounding alone (concept-guided) gets to 0.60/1.0 expert-rated correctness; adding a verification
  layer that rejects unconfirmed claims (Caïssa AI) gets to a 93.13% hit rate on tactic detection
  specifically. Neither number is "never false" — which is why this design removes language-model
  generation of the *claim* altogether and keeps it only, optionally, for surface wording of an
  already-verified fact (§6).
- **Comparing before/after concept scores isolates "what changed" cheaply.** We already compute the
  full evaluation and the search line for both the played move and the engine's alternative — the
  marginal cost of also comparing structural predicates (material, king-safety proxies, pawn
  structure) before and after is small, and it is exactly the signal concept-guided commentary
  found most informative.
- **`python-chess`'s primitives are exact, not heuristic**, for the predicates they cover (pin,
  attackers) — a pin either exists geometrically or it doesn't, so that class of claim can be made
  with 100% precision at near-zero cost, unlike anything requiring a search or a language model.
- **A minimum eval-delta gate**, already used by `python-chess-annotator`, keeps the feature silent
  on the vast majority of moves where no single cause explains a small, noisy swing — which is the
  correct behaviour, not a missing feature (§6).

## 3. What they do badly

- **ChessGrammar publishes no algorithm detail, no accuracy numbers, and no licence** — its two-phase
  shape (geometric candidate, then forced-sequence confirmation) is evidence the approach is
  buildable, not a specification; nothing from it is ported here (§9).
- **Concept-guided commentary still needs a paid, hosted LLM (GPT-4o) for every sentence**, and even
  with concept grounding, the paper's own error analysis names "wrong understanding of
  positional/long-term advantage" as the largest remaining failure class, at 28% — the exact class of
  claim this design refuses to attempt in free form at all (§6, "must not attempt").
  Source: https://arxiv.org/html/2410.20811v1
- **Caïssa AI's trust comes from heavy infrastructure** — a fine-tuned LLM, Neo4j, SWI-Prolog, a
  LangGraph orchestration layer — none of which fits inside an offline browser Web Worker in an
  MIT-licensed bundle (`chess/SPEC.md` explicitly rules out shipping any GPL engine or heavy runtime
  dependency in the client bundle).
- **`python-chess`'s own issue tracker documents a real false-positive trap**: "pinned pieces still
  count as attackers," meaning a naive attacker/defender count for a hanging-piece check will
  misjudge any position where the *defender* is itself pinned and cannot legally recapture — this
  must be corrected in our detector, not inherited (§7).

## 4. What we should copy conceptually

- **Detect symbolically first; only ever describe a fact that a deterministic check has confirmed.**
  This is the single idea worth taking from the whole survey, and it is the spine of §6.
- **Before/after comparison, not single-position description**, for isolating what a move actually
  changed (concept-guided commentary's core mechanism).
- **A verification pass that can veto a claim**, Caïssa AI's contribution, reimplemented here as
  "the detector itself only fires on fully-verified predicates" rather than as a second model
  checking a first model's output — cheaper and strictly more reliable, since there is no first,
  unverified generation step to check.
- **A minimum-delta gate before emitting anything**, `python-chess-annotator`'s pattern, extended in
  §6 to a per-feature confidence bar, not just a global eval threshold.

## 5. What we can do better

- **No hosted LLM in the loop for the factual claim, at all.** Every system surveyed either accepts a
  known error rate (concept-guided: 28% on the hardest category) or pays for heavy verification
  infrastructure (Caïssa AI). This design instead treats "detector fires with full confidence" as the
  *only* path to a sentence — if no detector fires, the feature shows the number and stays silent on
  the reason, which is strictly more honest than a plausible-sounding guess.
- **Runs for free, offline, in the Web Worker we already ship**, on every move of every game, because
  the search and evaluation this depends on already run there (`chess/SPEC.md` Part K2) — no per-call
  cost, no network dependency, no rationing.
- **Independently recomputable.** Because the ruleset is a versioned, published spec (not a model
  checkpoint), and the game record is signed, a stranger's browser can re-derive the identical
  sentence from the identical position — matching the "recompute button" principle `chess/SPEC.md`
  Part 0 makes the product's actual pitch, and something no system surveyed offers.

## 6. What is technically required

**Inputs available for every move, already computed:** the position before the move (FEN/board
state), the played move, the engine's principal variation from that position (which supplies its
preferred move and, if applicable, a forced mate line), the evaluation before and after the played
move, the evaluation after the engine's preferred move, and — for material/structural comparison —
full piece lists before and after.

**The rule that governs every feature below:** a sentence is emitted only if (a) a named predicate
over the position and/or search output returns true with no ambiguity, and (b) the resulting
eval-delta clears a minimum gate (reusing `python-chess-annotator`'s ~75–150cp / ~7.5-win% band as the
starting point, tunable). If no predicate fires, the UI shows the number only — no sentence. Predicate
false positives are prevented by testing each detector against a fixed regression suite of known
positions (mirroring how a chess engine's move generator is perft-tested) before it ships, and by
requiring every "the opponent can now do X" claim to be confirmed by the engine's own search output
for the resulting position, never by static geometry alone.

**Feature tiers, cheapest and most reliable first:**

| # | Feature | Detection | Cost / reliability | Template |
|---|---|---|---|---|
| 1 | **Missed mate in N** | Read directly off the search output: engine's PV from the position before the move returns a mate score that the played move does not achieve or that the opponent can now inflict. No inference — the number is already exact. | Free, 100% reliable — this is the cheapest and safest feature in the whole design. | "{engine move} was mate in {N}: {line}." |
| 2 | **Hanging piece / free capture** | Count attackers and *legally-recapturing* defenders of the moved-to (or newly undefended) square after the move, correcting for `python-chess`'s documented trap: a defender that is itself absolutely pinned to its king along the recapture ray does not count. Confirm the capturing side actually comes out ahead via a static-exchange-style resolve (walk the capture sequence in attacker-value order), not attacker-count alone. | Cheap, geometric, near-100% reliable once pinned-defender correction and SEE resolution are applied (§7 covers the remaining edge cases). | "leaves the {piece} on {square} undefended; {opponent's move} wins it for free." |
| 3 | **Passed pawn created or given away** | Purely geometric, textbook-definitional: a pawn is passed if no enemy pawn occupies its file or an adjacent file on any rank ahead of it. Compare the predicate before and after the move for every pawn touched by the move or by the capture it allowed. | Free, 100% reliable — this predicate has no ambiguity in standard chess. | "creates a passed pawn on {file}." / "gives Black a passed pawn on {file} by trading off its last blocker." |
| 4 | **Pin** | Direct port of `python-chess`'s `pin()` semantics: ray-cast from the king outward along each of the 8 directions; if the first piece is an opponent's and the next piece on the same ray is a friendly slider that could capture along it, the first piece is pinned. Exact geometry, no search needed. | Cheap, 100% reliable for absolute pins to the king. Relative pins (to a piece other than the king) require an added value comparison and are lower-confidence — flagged separately, not merged into the same template. | "pins the {piece} to the king along the {rank/file/diagonal}." |
| 5 | **Skewer** | Same ray-cast as a pin, inverted: the more valuable piece is the one directly attacked and must move, exposing a less valuable piece behind it on the same ray. Requires confirming the front piece has no legal way to interpose or capture the attacker — a legal-move check, not a guess. | Cheap–moderate, reliable once the legal-move check is included; skipping that check produces false positives (§7). | "skewers the {front piece} and the {back piece} on the {line}." |
| 6 | **Fork** | Candidate: does one piece, after the move, attack ≥2 enemy pieces whose combined value exceeds what could be saved in one move? Must then be **confirmed against the engine's own search**, not geometry alone: verify no single reply saves both attacked pieces (including counter-forks, in-between checks, or a bigger threat elsewhere) by checking that the position after the opponent's best defensive try, per search, still shows a material loss. | Moderate cost (needs a shallow search of defensive replies), reliable only with that search confirmation — geometry alone produces false positives whenever a counter-resource exists (§7). | "the {piece} forks the {king/piece} and the {piece} on {squares}; no single reply saves both." |
| 7 | **Discovered attack** | Moving piece X reveals an attack from piece Y along a ray that piece X previously blocked. Detected by comparing the attacker set on the relevant piece/king before and after the move restricted to sliding pieces whose line was exactly the vacated square. | Cheap–moderate, reliable — this is geometry plus a before/after set comparison, not search-dependent. | "moving the {piece} uncovers an attack from the {piece} on {target}." |
| 8 | **Back-rank weakness** | King has zero legal non-capturing escape squares on its own rank/adjacent ranks (blocked by its own pawns/pieces or those squares are themselves attacked), and an open file or diagonal exists for an opponent rook/queen to reach the back rank. Must be confirmed by the search actually finding the resulting mate or decisive material loss — the geometric shape alone ("the king looks boxed in") is not sufficient to claim a back-rank weakness is *exploitable* this move. | Moderate — geometry is cheap, but the "exploitable now" claim requires search confirmation to avoid false alarms in positions where a spite check or the rank isn't actually reachable. | "the back rank is weak: {king} has no escape square, and {opponent move} threatens mate." |
| 9 | **Lost tempo** | Compare the played line to the engine's PV: does the moved piece get attacked by the opponent's natural reply and have to move again, at a position the search rates measurably worse than the PV's continuation, where the PV's move did not require the same piece to move twice? Emit only when the resulting eval loss clears the minimum gate — "lost a tempo" as a label without a measured cost is not a verifiable claim. | Moderate — needs PV comparison, not just static geometry; reliable when gated on measured eval loss rather than asserted from a heuristic pattern alone. | "moving the {piece} again here loses a tempo — {opponent move} attacks it a second time, and the position that results is measurably worse than after {engine move}." |
| 10 | **Entombed / trapped piece** | Enumerate legal moves for a specific piece across several plies of the engine's PV; if that piece has zero legal moves (or only moves that lose it) across the depth searched, and this is new as of the played move, flag it. Expensive relative to the above — needs multi-ply legal-move enumeration, not a single-position check — and its confidence is bounded by search depth: a piece "trapped" at depth 6 may have an escape at depth 12 the search didn't reach. | Expensive; medium-reliable — only claim "trapped for now, to the depth searched," never "trapped, full stop," unless the search is exhaustive (rare outside the endgame). | "the {piece} on {square} has no safe square to move to, as far as the engine has searched." |
| 11 | **Trade that helps the opponent** | Compare eval before and after a materially-equal exchange sequence. If the post-trade eval favours the opponent despite equal material, check for a *specific, verifiable* structural cause — the trade opened a file/diagonal toward our own king, or removed the only defender of a square the opponent immediately occupies, or converted the opponent's previously-bad piece into a good one by removing its counterpart. Only name the cause if one of these specific, checkable conditions holds; otherwise report the eval swing with no invented reason. | Moderate–expensive depending on which structural check is run; reliability is exactly as good as the specific sub-check used — this is the feature most tempting to over-claim on, so §7 treats it as the primary false-positive risk. | "trading here removes {piece}'s last defender of {square}, and {opponent} occupies it next move." / (fallback, no cause confirmed) "this trade favours {opponent} by {swing} according to the engine — no single cause could be confirmed." |
| 12 | **Missed defensive resource** | Only ever reported when the engine's own search, at the depth already run for the position, finds a specific alternative move for the player that holds the position to within the "no significant loss" band, and that move was available but not played. This is a report of what search already found, not a new claim invented for the explanation — expensive only in the sense that it requires the search to have looked at the position at all (which it already has, since we evaluate every move per `chess/SPEC.md` Part K2). | Free once the search has run (it already has); reliable exactly to the confidence of the underlying search — deeper search raises confidence, but the claim is always scoped to "as far as searched." | "{alternative move} held the position; the engine finds no way for {opponent} to press an advantage after it, to the depth searched." |

**What must never be attempted, at any tier:**

- **Any claim about the player's intention, psychology, or state of mind** ("you got greedy," "you
  missed this because you were low on time," "you panicked") — this is unverifiable from a position
  and a move, full stop, regardless of detector sophistication. Coaches are right that the *cause* of
  a blunder is a thought-process gap (`coaching.md` §1), but a position-and-move pair cannot diagnose
  a thought process; only the player's own reflection can, and the feature should prompt for that
  rather than assert it.
- **Free-form "positional" or "strategic" judgment beyond what a named, checkable predicate covers.**
  The concept-guided commentary paper's own finding — "wrong understanding of positional/long-term
  advantage" is the single largest remaining error class at 28%, even with concept grounding and a
  strong LLM — is direct evidence this category cannot be made reliable with current techniques.
  Source: https://arxiv.org/html/2410.20811v1. Anything not covered by tiers 1–12 above should surface
  only the raw eval number, never an invented reason.
- **Stating the engine's evaluation as objective chess truth rather than one model's assessment.**
  McGrath et al. show a single trained model's "opinion" of a position is not a stable ground truth
  even across its own training runs (`coaching.md` §3) — our engine's number is the best available
  signal, not an oracle, and template wording should reflect that ("the engine finds...", not "this
  position objectively favours...").
- **Any sentence produced by unconstrained language-model generation over the position itself.**
  Every system in the survey that does this — ChessCoach ("often wrong"), ungrounded GPT-4o (0.36
  correctness) — is measurably less reliable than the grounded alternative; this design has no
  language-model step in the truth-bearing part of the pipeline at all. If natural-sounding surface
  variation is wanted later, an LLM may be used only to *rephrase* an already-fully-specified,
  fully-verified template — never to select or invent the underlying claim.

## 7. What could break

- **False-positive fork/skewer detection from geometry without a defensive-reply check.** A piece
  that geometrically "forks" two others can still have both saved by an in-between check, a
  counter-fork, or a bigger threat the naive detector didn't consider — tiers 6 (fork) and 8
  (back-rank) explicitly require search confirmation of the resulting position for exactly this
  reason; shipping the geometric candidate alone without that confirmation is the single most likely
  way this feature says something false.
- **The pinned-defender trap.** `python-chess`'s own issue tracker documents that a pinned piece still
  counts as an "attacker" in its API — the same failure mode applies to *defender* counting in tier 2
  (hanging piece): a piece that appears to defend a square but is itself absolutely pinned cannot
  legally recapture, and a detector that doesn't exclude it will falsely claim a piece is safe when it
  is not (or vice versa). Source: https://github.com/niklasf/python-chess/issues/375. Mitigation:
  every "defended" check must confirm the defending move is *legal in the actual position*, not merely
  geometrically present.
- **Near-equal alternatives presented as a single decisive cause.** Chess.com's own Game Review is
  criticised for exactly this — picking one "best" move among several within ~0.30 of each other and
  "exaggerating the relative evaluation," per `game-review.md` §3 — so every tier above must gate on a
  minimum eval-delta and, where possible, confirm the engine's principal move has a real margin over
  the second-best line before naming it as "the" reason, not merely "a" reason.
- **The trade-that-helps-opponent feature (tier 11) is the highest-risk template for overclaiming a
  cause that isn't really there** — an eval swing after an equal trade can have no single clean
  structural explanation; the design's fallback ("no single cause could be confirmed") exists
  specifically to avoid inventing one, and must not be silently dropped for the sake of a more
  satisfying sentence.
- **Version drift.** If detector logic changes over time without versioning, a "Why?" sentence
  generated for an old game cannot be reproduced identically later — this is the same risk
  `game-review.md` §7 flags for classification-rule changes, and the same fix applies: version the
  ruleset and stamp the version into the record, per `chess/SPEC.md` Part 8's signed-record model.
- **Latency from the expensive tiers (6, 8, 10, 12) inside the Web Worker.** These require additional
  search beyond what's already computed for the eval bar; if run synchronously they can stall the UI.
  Mitigation: show the cheap, always-available tiers (1–5, and the raw eval number) immediately, and
  disclose the expensive tiers asynchronously once available — the same graduated-disclosure shape as
  Lichess gamebook hints (`coaching.md` §1), applied to computation cost rather than pedagogy.
- **Mislabeling a real tactic with the wrong name** (calling a double attack a "skewer," or a
  relative pin an absolute one) erodes trust exactly as much as a false claim about the position —
  each template's trigger predicate must match the textbook definition of the term precisely, not an
  approximation, and the regression-test suite (§6) must include known counter-examples for each term,
  not just positive examples.

## 8. What we can uniquely do because of Nimiq

- **Zero marginal cost, every move, forever.** The detectors and search this design depends on already
  run in the MIT engine shipped offline in the browser wallet (`chess/SPEC.md` Part K1/K2) — unlike
  every system surveyed (a hosted LLM call, a GPU-served fine-tune, a Neo4j/Prolog server), there is no
  per-explanation cost to ration, so "Why?" can run on every flagged move of every game by default.
- **Auditable, not just plausible.** Because the ruleset is a versioned public spec attached to a
  signed game record, a third party's browser can re-run the exact same detectors over the exact same
  position and get the identical sentence — the same "recompute button" principle that is the
  product's entry pitch (`chess/SPEC.md` Part 0) applied to coaching output specifically, which no
  product or research system surveyed offers (all are either proprietary or checkpoint-dependent and
  non-reproducible).
- **Ties directly into a wallet-native practice loop.** Because the detector output is structured, not
  free text, a "review your own misses" mode (spaced-repetition puzzles built from a player's own
  detected tier-2/4/5/6 mistakes) is a natural extension that needs no new infrastructure — the same
  detectors that generate the "Why?" sentence also generate the puzzle, tied to the player's own signed
  game history rather than a canned course, which is not available to any product surveyed in
  `coaching.md`.

## 9. Licence and reuse verdict

- **ChessGrammar** — proprietary, no licence or algorithm detail published beyond a two-phase
  description; nothing ported, used only as evidence the geometric-candidate-then-search-confirmation
  shape is buildable. Source: https://dev.to/stevejvv/i-built-an-api-that-detects-chess-tactical-patterns-from-fen-and-pgn-5ef0
- **`python-chess`** (GPL-3.0, `LICENSE.txt` confirmed at
  https://github.com/niklasf/python-chess/blob/master/LICENSE.txt) — the `is_pinned`/`pin`/`attackers`
  *semantics* are read here as a functional specification only, per `chess/SPEC.md` Part L1 (copyright
  protects expression, not function/algorithm); our own board representation is a separate
  implementation and no `python-chess` code is used, since the client bundle must stay MIT.
- **`python-chess-annotator`** (GPL-3.0) — the numeric thresholds (blunder/mistake/dubious bands, the
  7.5-win% annotation gate) are cited as public facts about a public tool's tuning, reused as a
  starting point for our own values, not as code.
- **Concept-guided chess commentary** (`ml-postech/concept-guided-chess-commentary` — **no LICENSE
  file found in the repository**) and **Caïssa AI** (GPL-2.0, `MazenS0liman/Caissa-AI`) — cited for
  their published findings (correctness numbers, error-category breakdown, detect-then-verify
  architecture) as unprotected ideas per `chess/SPEC.md` Part L1; no code from either repository is
  used.
- **This design's core departure from every source above**: it contains **no language-model text
  generation in the truth-bearing path at all** — only deterministic predicate evaluation and template
  fill — which means there is no third-party model weight, generation code, or training corpus
  embedded anywhere in the feature, sidestepping the licence exposure every other system surveyed
  carries (a served model checkpoint, a GPL/AGPL-licensed reference implementation, or a
  permission-gated dataset).
