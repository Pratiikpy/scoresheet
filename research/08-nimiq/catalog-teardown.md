# Catalog teardown — a walk of shipped Nimiq Mini Apps

**Method:** the three verified Cycle 1 winners (`clones/nspace`, `clones/game`, `clones/nimquest`) were torn down at the source-code level — files opened, line numbers checked. The rest of the catalog was inspected two ways: (1) structured metadata pulled from the live catalog API snapshot (`catalog_apps.json`, `75` apps, fetched `28 Aug 2026`) and (2) a live plain-HTTP fetch of ten notable app URLs performed this session. **Caveat stated up front and repeated where relevant: a plain fetch only sees server-rendered/inlined markup — real wallet-connect dialogs, loading spinners, and post-JS navigation are invisible to it for any client-side SPA.** Where that limit applies, it's called out explicitly rather than guessed past.

## 1. What they do

### The three verified winners (full source access)

**Nimiq Space (`nspace`) — Social, Cycle 1 1st place.** A Three.js multiplayer isometric world: walk, chat, build, unlock rooms, play mini-games, earn NIM. Monorepo (`client`/`server`/`payment-intent-service`/`payout-service`/`analytics-service`). **Navigation pattern:** single persistent game canvas, no page routing — panels/overlays (stats, quests, leaderboard, wallet prompt) mount and unmount over the canvas rather than navigating away from it. **Wallet connection:** `isNimiqPayMiniApp()` checks `window.nimiqPay != null`; inside Nimiq Pay it signs via the injected `@nimiq/mini-app-sdk` (`nimiq.sign()`), outside it falls back to `HubApi.signMessage()` (`hub.nimiq.com` popup) — same login message (`Login:v1:${nonce}`), two transports, decided at call time (`clones/nspace/client/src/auth/nimiq.ts`, read directly). A dismissible "Get a Nimiq wallet" overlay (`showGetWalletPrompt`) offers "Sign in with wallet" plus App Store / Play Store / `nimpay.app` links for guests who have no wallet yet — and a *non*-dismissible full-page variant for when a guest's play-space has expired (`clones/nspace/client/src/invite/walletOnboarding.ts`). **Loading state:** a shared spinner (`nimiqHexLoaderSvg`) reused directly from the Keyguard's own MIT-licensed hex-loader asset, paired with a "Signing in" label whose trailing dots animate through `.`, `..`, `...` every 400ms (`clones/nspace/client/src/ui/walletSigningUi.ts`) — with a dedicated `isSigningUserCancelledError()` helper that recognizes six different wallet-cancellation phrasings as a normal outcome, not an error state.

**NimJump (`game`) — Games, Cycle 1 2nd place.** Godot 4.7 arcade platformer with a Go backend doing server-side replay verification (client-authority-proof pattern). **Navigation pattern:** native game UI panels (StatsPanel, QuestPanel, LeaderboardPanel), not a web page structure. **Wallet connection:** every "Connect Wallet" entry point across all panels funnels through one shared function (`NimiqJS.gd::request_account`); when `window.nimiq` genuinely doesn't exist (i.e. not running inside Nimiq Pay), it fires one shared install-prompt popup rather than letting each button fail silently — a fix the code's own comment documents as a deliberate response to a prior "looks broken/dead" bug. A plain-browser (non-Nimiq-Pay) visitor gets a Hub-API popup fallback instead, for both sign-in and payment (`start_hub_sign`, `start_payment` in the same file) — explicitly gated to fire synchronously from a real user gesture so the popup isn't blocked, with a documented COOP/COEP fix for a prior "Connection was closed" bug. **Loading state:** polling loops (`await_request_account`, `await_sign`, `await_payment`) at 100ms intervals with generous timeouts (30s for account requests, 60–90s for signing/payment, i.e. sized for a human approving inside the wallet app, not a network round-trip).

**NimQuest (`nimquest`) — Education, Cycle 1 3rd place.** Cloudflare Workers + D1, vanilla ES modules, no framework. A "learn Nimiq, prove it, sign a message" quiz app — **moves zero NIM at any point**, the only proof is a signed one-time challenge (`clones/nimquest/apps/web/main.js`, `sign()` via `init()` from `@nimiq/mini-app-sdk`). **Navigation pattern:** hash/path-based routing in ~2,700 lines of vanilla JS (`/quests/:id`, `/proof/:id`), no SPA framework. **Wallet connection:** deferred until the specific "prove you did this" moment inside a quest, not gated up front — quests are readable and completable before any wallet action is required. **Loading/offline state:** `installConnectivityBanner()` — a persistent, dismissal-free banner reading *"You're offline. Saved lessons still work, but grading, proof, sync, and shared receipts need a connection."* with a Retry button, driven by `navigator.onLine` and the `online`/`offline` browser events (read directly, `apps/web/main.js`).

## 2. Why it works

**The winners share one trait the shell-only catalog apps lack: every wallet-adjacent moment has an explicit, human-legible state.** Nimiq Space never leaves a user watching a blank screen during sign-in — the hex-loader spinner plus animated "Signing in..." text is always paired with the async call, and cancellation is treated as a first-class, non-error outcome (`isSigningUserCancelledError`). NimJump never lets a "Connect Wallet" tap do nothing — it either succeeds or explicitly tells the visitor to open the app. NimQuest never lets a lost connection look like silence — the offline banner names exactly what still works (saved lessons) versus what doesn't (grading, proof, sync).

**TipWall and VeriLock are the two catalog apps (of the ten fetched) that actually communicate value before any wallet action, in markup a plain visitor or a search crawler can see at all.** TipWall's inlined "1. Choose your link → Continue to wallet" sequencing tells a cold visitor exactly what's about to happen and in what order, before any dialog appears. VeriLock goes further — its entire pitch, FAQ, and privacy claims are static-first, wallet mentioned only as an optional enhancement to a flow that already makes sense without one.

**All three winners defer or entirely avoid moving real value where a signature suffices.** NimQuest's zero-NIM proof-of-completion is the clearest case, but Nimiq Space's guest mode (playable before any wallet exists) and NimJump's Hub-API browser fallback are the same instinct: don't make the wallet the gate to trying the thing.

### What "feels native" means in this container — derived from the pattern above, not asserted

Read across the winners and the ten fetched apps, "feels native" resolves to a small, consistent set of behaviors, not a look:

1. **Every wallet-adjacent async call has a visible, branded waiting state** — never a frozen button or blank screen. (Nimiq Space's shared spinner; NimJump's polling loop sized to real approval time, not network latency.)
2. **A missing/rejected provider is communicated, not silently absorbed.** (NimJump's install-popup chokepoint; both winners treating user-cancel as normal, not an error toast.)
3. **The app explains itself before it asks for anything.** (TipWall and VeriLock's static-first pitch copy; NimQuest's quests are readable before any wallet action is required.) The apps that fail this (SteadyStreak's bare "Loading…", the pure-SPA-shell majority) give a cold visitor — including, per `SKOOL_FULL_ARCHIVE_FINDINGS.md`'s confirmation that judges test the live product as a real user, a *judge* — nothing to evaluate on first contact.
4. **A browser-outside-Nimiq-Pay visitor is treated as a real, supported case, not an afterthought**, wherever the concept allows it (both winners' Hub-API fallback paths).
5. **Sensitive actions are visually distinct from everything else** — Nimiq's own native confirmation dialog is the actual gate (`NIMIQ_DEV_DOCS_FULL_REFERENCE.md` §1: "mini apps cannot bypass" it), so the app-side job is to make the *lead-up* to that dialog feel considered (a labeled step, a spinner, a clear cancel path) rather than to imitate the dialog itself.

## 3. What they do badly

- **The dominant failure mode in the catalog is simply showing nothing.** Seven of nine reachable fetched apps returned a bare `<title>` and no other content — no meta description, no static fallback, no `<noscript>` message. A search engine, a link preview, or (per the QA standard this research follows) a judge's first cold click sees nothing to react to.
- **SteadyStreak's "Loading SteadyStreak…" is a genuine dead end if that's ever what a visitor is served** — there's no fallback content, no timeout message, nothing indicating the app might simply have failed to load versus still being on its way.
- **NIMGA's domain didn't respond to a live request this session at all** — an outright connection failure, whatever the cause. Combined with the 9 (as of 28 Aug) / 11 (as of 29 Aug) domains already confirmed dead in the catalog snapshot (`WINNER_TEARDOWNS_VERIFIED.md` §6; `CYCLE_2_LIVE_FIELD_20260829.md` §2), domain rot is a real, ongoing, and worsening pattern in this catalog, not a one-time snapshot artifact.
- **BodyDouble's Cycle 2 submission demo shows literally no wallet/EVM connection on first paint** despite the pitch being built entirely around a USDT stake — the mechanic that's supposed to be the point of the app isn't visible at all in the shipped demo (`CYCLE_2_LIVE_FIELD_20260829.md`, direct quote above).
- **Quick proof nim tip jar's submitted demo link routes a cold judge straight into an internal setup form** (three department email addresses) instead of anything resembling the product's actual value — a self-inflicted violation of "onboarding: zero to using it in under 60 seconds" from a team that otherwise built something real (same source).
- **None of the nine reachable fetched apps showed an actual rendered "Connect Wallet" control in raw markup** — even the three with real inlined copy only *describe* a coming wallet step. That is consistent with these being genuine SPAs (the control likely renders after JS executes) but it also means none of them offer any content-visible signal of *how* wallet connection will feel until a visitor is already deep into a JS-loaded session — an unverifiable-but-plausible risk for anyone relying on link-preview or SEO discovery.

## 4. What we should copy conceptually

- **A single, shared "no provider" chokepoint with one clear message**, exactly like NimJump's `request_account` — every entry point into "connect wallet" in Scoresheet should resolve through one function that knows how to fail loudly and helpfully, not several buttons that each fail silently in their own way.
- **Treat wallet-cancel as a normal outcome with its own UI state**, not an error path — both winners do this explicitly (`isSigningUserCancelledError`'s six recognized phrasings; NIMIQ_DEV_DOCS_FULL_REFERENCE.md §11's own "treat the cancellation case as a normal outcome, not a bug").
- **Sequence the pitch before the wallet prompt, in visible markup** — TipWall's "1. Choose your link → 2. Continue to wallet" and VeriLock's fully static-first pitch are the two catalog apps that actually pass the "a cold visitor understands the value before doing anything" test. Scoresheet's landing state (whatever a judge or a first-time user sees, inside or outside Nimiq Pay) should be pre-renderable content, not a blank shell waiting on JS + a provider.
- **Offer a genuine no-wallet-required path where the concept allows it** — Nimiq Space's guest mode and NimQuest's read-before-sign quest structure both prove a real product doesn't have to gate everything behind a connected wallet on first contact.
- **Size timeouts and polling to human approval time, not network latency** — NimJump's 60–90s windows on signing/payment awaits reflect that a person is reading and approving inside a separate wallet UI, not that a server is slow.
- **A persistent, specific offline/degraded state**, not a generic spinner or silent failure — NimQuest's banner names exactly what still works and what doesn't during an outage.

## 5. What we can do better

- **Ship real server-rendered/pre-rendered content for the pre-wallet state**, something 7 of 9 fetched catalog apps conspicuously don't do. A pre-rendered (SSG/SSR) landing/first-screen with the pitch, a static preview of what the app does, and clear copy about what happens next would put Scoresheet ahead of nearly the entire observed catalog on first-contact quality alone — measurable directly against this same fetch method a judge or reviewer might also use.
- **Never let "loading" be the only visible word on screen.** SteadyStreak's failure mode is trivially avoidable: pair any loading state with at least the app's actual pitch or a skeleton of the real UI, not a bare string.
- **Make the wallet-connect moment content-visible, not purely JS-materialized**, at least as a static illustration or copy block — none of the ten fetched apps do this, so doing it distinguishes Scoresheet without requiring guesswork about what "good" looks like (there's no positive example to copy here, only negative examples to avoid).
- **Treat the submitted competition demo URL as a first-class deliverable, tested cold, the way the two Cycle 2 examples above did not.** Both BodyDouble and Quick Proof lost real ground on the exact thing this document is checking for — what a cold, unauthenticated fetch/visit actually shows.
- **Verify domain reachability is a maintenance task, not a launch task** — 9 apps dead at 28 Aug became 11 by 29 Aug in the live catalog (`CYCLE_2_LIVE_FIELD_20260829.md` §2), and NIMGA failed outright this session. Whatever hosting Scoresheet uses, monitoring uptime past the submission date is table stakes the catalog shows most entrants don't meet.

## 6. What is technically required

- A build target that produces **real HTML on first response** for at least the pre-wallet landing state — e.g. Vite's SSG/prerender output, Next.js static export, or an equivalent — rather than shipping only a `<div id="app">` shell. This is the single concrete technical gap separating VeriLock/TipWall from the seven shell-only apps observed.
- **One shared wallet-connection entry function** (mirroring `NimiqJS.gd::request_account`) that all UI surfaces call into, so "no provider" and "user cancelled" are handled once, consistently, everywhere in the codebase.
- **A `navigator.onLine`-driven connectivity banner** (mirroring `nimquest`'s `installConnectivityBanner`), scoped to name exactly which Scoresheet features degrade offline (e.g. "reviewing a saved game still works; submitting a result needs a connection").
- **Timeout/polling values tuned for human wallet-approval time** (30–90s ranges, per NimJump), not default fetch timeouts.
- **A visible spinner/waiting asset for any provider call that can take real time** — reusing or closely mirroring the Keyguard's MIT-licensed hex-loader (already reused once, precedent established by `nspace`) is a legitimate, low-risk option.

## 7. What could break

- **A pre-rendered landing state can drift out of sync with the actual app state** if not tested — e.g. showing stale "how it works" copy after a real UX change. Needs to be part of the same release checklist as the app itself, not a one-time asset.
- **Domain/hosting rot is the single most common failure mode observed in this catalog** (11 of 75 apps dead as of the most recent snapshot, one more failing outright this session) — whatever host Scoresheet uses needs monitoring past the 18 Sep 2026 deadline, given the stated 12-month maintenance expectation (`CLAUDE.md`, project instructions).
- **A shared wallet-connection chokepoint is only as good as its error taxonomy** — if new failure modes appear (e.g. a timeout distinct from an explicit rejection) and aren't added to the shared handler, the "one clear message" benefit degrades back into per-surface guessing, the exact problem NimJump's fix addressed.
- **Testing this document's own method (a cold plain-HTTP fetch) is not the same as testing the real WebView experience** — none of the ten live fetches this session can confirm what actually renders inside Nimiq Pay itself; that requires the app installed and tested as a real user, which this research pass did not do (out of scope for a research-only task). This is a real gap this document does not close.

## 8. What we can uniquely do because of Nimiq

- **Chess has no incumbent in the 75-app catalog at all** — the closest neighbors by mechanic (PlayNimiq's skill-based games, NIM Duel) are casual/arcade, not a structured, server-verified competitive game with an existing global rating culture. This is a genuinely open lane, not a crowded one (cross-checked against the full saturation map in `CYCLE_2_LIVE_FIELD_20260829.md` §3 — chess/board games appear in none of the "heavily crowded" clusters).
- **A signed-message-only result/rating-proof mode**, following NimQuest's zero-NIM precedent exactly, lets Scoresheet offer a genuinely free, wallet-verified competitive mode alongside any staked mode — no other catalog entry combines "skill-verified" with "zero-NIM proof" the way NimQuest's *education* app does, and nothing in Games does it at all.
- **A stake-per-game or stake-per-tournament mechanic priced in feeless NIM** is economically viable at stakes far smaller than any USDT/Polygon-based catalog competitor (XcrowHub, TalentOS AI, Piggy) could offer, because Nimiq settlement is free — directly relevant to a low-stakes casual-chess use case none of the observed Finance-category apps are built for.

## 9. Licence and reuse verdict

- The three winners (`nspace`, `game`/NimJump, `nimquest`) are **all MIT-licensed**, confirmed via each repo's `LICENSE` file (`WINNER_TEARDOWNS_VERIFIED.md` §1, cross-checked directly this session against `clones/nspace`, `clones/game`, `clones/nimquest`). Reading their source for patterns (as this document does) and porting small, clearly-attributed snippets (e.g. the shared wallet-chokepoint shape, the offline-banner pattern) is licence-safe.
- **None of the ten live-fetched catalog apps' source was read or copied this session** — only their public HTTP responses were observed, which carries no licence implication either way. Their `github_url` fields (present for most, per `catalog_apps.json`) would need individual licence checks before reusing any of their code directly; **not done here, NOT VERIFIED per-app**, and out of scope since no code from them was used.
- **Verdict:** safe to draw UX/behavioral conclusions from any publicly observable app (live fetch or in-app use) without licence concern — that's observation, not reuse. Direct code reuse is only confirmed safe for the three MIT-licensed winners; treat every other catalog app's source as licence-unknown until individually checked.
